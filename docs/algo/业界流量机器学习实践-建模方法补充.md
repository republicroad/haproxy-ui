## 二、建模范式分类：按任务划分

网关/负载均衡流量 ML 不是一个问题，而是**八个不同问题**，各自有不同的建模选择：

| # | 任务 | 输入 | 输出 | 延迟预算 | 业界主流方法 |
|---|------|------|------|---------|-------------|
| 1 | 指标异常检测 | 时间序列（RPS/错误率/延迟） | 异常点/区间 | 秒-分钟 | STL/SARIMA/谱残差 |
| 2 | L7 攻击检测（客户级） | 每客户流量画像 | 告警+签名 | 分钟级 | 每客户基线模型 |
| 3 | 载荷攻击分类 | 请求内容特征 | 攻击类别/分数 | 毫秒（内联） | 梯度提升树/ONNX 小模型 |
| 4 | Bot/人机区分 | 指纹+行为遥测 | 评分 0-99 | 毫秒（内联） | CatBoost/自监督序列模型 |
| 5 | 容量预测与扩缩容 | 历史负载 | 未来负载预测 | 分钟-小时 | Holt-Winters/集成预测 |
| 6 | 模型自我更新 | 新流量分布 | 更新后模型 | 离线 | 在线学习+漂移检测 |
| 7 | 会话行为分析 | 请求序列 | 异常序列 | 准实时 | n-gram/HMM/Embedding |
| 8 | 流量工程/调度 | 全网需求矩阵 | 路由/限速决策 | 秒级 | LP+ML 加速（RL 未生产） |

**关键洞察**：业界没有任何单一模型同时解决这 8 个任务。生产系统全部是**多模型分层组合**（与《轻量流式异常检测》的快慢路径架构一致）。

## 三、范式一：时序预测型异常检测

> 适用：网关 RPS、错误率、P99 延迟等**指标级**监控。前三篇文档的 Z-score 基线是静态/半静态版本，业界生产系统大量使用**预测型**（预测下一个点，实际值偏离预测带即告警）。

### 3.1 Datadog 三算法（公开文档）

来源：[Introducing Anomaly Detection](https://www.datadoghq.com/blog/introducing-anomaly-detection-datadog/)、[Anomaly Monitors](https://docs.datadoghq.com/monitors/types/anomaly/)

| 算法 | 原理 | 特点 | 适用 |
|------|------|------|------|
| **Basic** | 滚动移动平均 + sigma 带 | 快速适应，异常会被逐渐吸收进基线 | 无明显周期的短窗口指标 |
| **Agile** | **鲁棒版 SARIMA**（Datadog 原话："a robust version of the classical SARIMA model"） | 预测下一个点，对异常敏感 | 有日/周周期的流量 |
| **Robust** | STL 季节-趋势分解，预测带极稳定 | 长异常不会污染基线；默认周周期，**需 3 周历史** | 有强周期性的关键指标 |

```python
# Agile 类算法的本质（伪代码）
# SARIMA(p,d,q)(P,D,Q,s) 对每个时间点：
#   1. 用历史窗口拟合季节性 ARIMA
#   2. 预测下一值 ŷ 和置信带 [ŷ-kσ, ŷ+kσ]
#   3. 实际值 y 落在带外 → 异常
# 鲁棒化：用中位数/MAD 替代均值/σ，防止异常本身污染模型
```

### 3.2 Microsoft 谱残差 SR / SR-CNN（KDD 2019 Oral）

来源：[Time-Series Anomaly Detection Service at Microsoft](https://arxiv.org/abs/1906.03821)、[SR-CNN in Azure Anomaly Detector](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/overview-of-sr-cnn-algorithm-in-azure-anomaly-detector/982798)、[ML.NET SrCnnAnomalyEstimator](https://learn.microsoft.com/en-us/dotnet/api/microsoft.ml.transforms.timeseries.srcnnanomalyestimator)

**核心思想**：从视觉显著性检测借来的方法——对序列做 FFT，取对数幅度谱，计算"谱残差"（谱中不可预测的部分），逆变换回时域得到显著性图，显著点即异常。

```
输入序列 x
  │
  ▼
FFT(x) → 幅度谱 A(f)，相位谱 P(f)
  │
  ▼
谱残差 R(f) = log(A(f)) − avg_log(A(f))    ← 对数谱减局部平均
  │
  ▼
显著图 S(x) = IFFT(exp(R(f)) · exp(i·P(f)))
  │
  ▼
S(x) 高的点 = 异常（O(n log n)，无参数、无训练）
```

**SR-CNN**：在 SR 输出上跑 CNN 判别器，**用全合成数据训练**（在正常序列上注入人工异常点），不需要真实标注。微软生产数据上 F1 比 SR 提升 >20%。

**工程意义**：
- SR 是**无参数、O(n log n)、免训练**的——非常适合网关指标这类"序列量巨大、单条价值低"的场景
- 微软内部 200+ 团队使用，每分钟处理数百万条时间序列
- 已有 ML.NET 实现（`SrCnnAnomalyEstimator`），可直接集成进 .NET 网关监控
- 这是**比 LSTM 更适合指标监控的选择**：单序列 LSTM 需要训练，SR 零成本适用任意新序列

### 3.3 开源时序异常检测库（运维界常用）

| 库 | 技术 | 出处 |
|----|------|------|
| **Twitter AnomalyDetection**（R） | **S-H-ESD**：STL 分解 → 对余项做广义 ESD 检验，用**中位数+MAD**（鲁棒统计） | [Twitter 工程博客](https://blog.x.com/engineering/en_us/a/2015/introducing-practical-and-robust-anomaly-detection-in-a-time-series) |
| **Yahoo EGADS**（Java） | 两阶段：时序建模模块（ARIMA 等预测期望值）+ 异常检测模块（ExtremeLowDensityModel 等多检测器）+ **自动阈值确定** | [GitHub](https://github.com/yahoo/egads)、KDD 2016 论文 |
| **Netflix RAD**（Surus 内） | **鲁棒 PCA** 分解出低秩（正常模式）+ 稀疏（异常）矩阵 | [GitHub Netflix/Surus](https://github.com/Netflix/Surus) |
| **LinkedIn luminol**（Python） | 异常检测 + **相关性分析**做根因定位，逐点异常分数而非固定阈值 | [GitHub](https://github.com/linkedin/luminol) |
| **Uber PyOD**（Python） | 50+ 离群检测器（经典到深度），支持时序；PyOD 2 加入 LLM 辅助选模型 | [文档](https://pyod.readthedocs.io/) |

### 3.4 Netflix Atlas 的轻量做法

来源：[Atlas 文档](https://netflix.github.io/atlas-docs/overview)

Atlas（Netflix 内存级多维时序数据库）不使用深度模型，而是用**双重指数平滑（DES）预测线**：实际 RPS 低于 DES 预测线即告警。证明**简单方法 + 好的维度数据模型**在监控场景已够用。

### 3.5 与已有 Z-score 基线的关系

| 维度 | Z-score 基线（已有文档） | 预测型（本节） |
|------|------------------------|---------------|
| 基线形态 | 静态均值±kσ（按窗口滚动） | 动态预测值±预测置信带 |
| 周期建模 | 需手动分维度（工作日/周末） | SARIMA/STL 内建周期项 |
| 趋势响应 | 漂移检测触发重算 | 每点自适应 |
| 计算成本 | O(1)/点 | O(window)/点（可用滑窗优化） |
| 建议用途 | 内联快路径硬阈值 | 慢路径指标告警（Datadog/Atlas 模式） |

## 四、范式二：每客户基线模型服务

> 适用：多租户网关/CDN 的 L7 DDoS 自适应防护。这是"行为基线"（已有文档）在**超大规模 SaaS** 形态下的进化：基线不是一个阈值，而是**每个客户一个独立训练的模型**。

### 4.1 Cloudflare：一天训练一百万个模型

来源：[Training a million models per day](https://blog.cloudflare.com/training-a-million-models-per-day-to-save-customers-of-all-sizes-from-ddos)、[Adaptive DDoS Protection](https://blog.cloudflare.com/adaptive-ddos-protection)

**做法**：
- 为**每个客户的每个流量属性**（按路径/国家/ASN 等分片）单独训练统计模型
- 特征映射到归一化超球面（normalized hypersphere），**异常分数 = 样本到球心距离**
- 每天重训 100 万个模型，模型小、训练快（单模型分钟级）
- 自适应 DDoS 防护结合 ML Bot Score 作为输入信号，区分"合法流量尖峰"与"自动化攻击"

**为什么每客户独立模型而不是全局模型**：不同客户的流量形态差异巨大（一个游戏站和一个 API 服务商的正常 RPS 分布完全不同），全局模型会互相污染。这与《行为基线构建详细流程》"多维度基线"的结论一致，只是把"维度"推到了极限（每客户每属性）。

### 4.2 Google Cloud Armor Adaptive Protection

来源：[Adaptive Protection 概览](https://docs.cloud.google.com/armor/docs/adaptive-protection-overview)、[Google Cloud 博客](https://cloud.google.com/blog/products/identity-security/improve-your-ddos--waf-defense-with-new-cloud-armor-features)

**架构（关键：带外检测）**：

```
请求 → Google 前端 → 后端服务
         │
         └─→（带外镜像）→ ML 检测管线
                            │
              ┌─────────────┴─────────────┐
              │ 模型组 A：基线异常检测      │  ← TensorFlow
              │ 输入：每后端服务的请求速率、 │
              │ 地理分布、UA 分布、请求模式  │
              └─────────────┬─────────────┘
                            │ 异常
              ┌─────────────┴─────────────┐
              │ 模型组 B：攻击签名生成      │  ← "几十个流量特征"
              │ 输出：疑似攻击签名 + 建议    │
              │ 的窄化 WAF 规则（可自动部署）│
              └───────────────────────────┘
```

**工程细节**：
- 训练期 ≥1 小时后告警才可靠（冷启动要求）
- 告警含每属性攻击可能性、攻击中占比、基线中占比（可解释性设计）
- 独特之处：**第二套模型生成"建议规则"**——不只检测，还给出修复动作（人工确认或自动部署）

### 4.3 AWS：从 Shield Advanced 到 WAF Anti-DDoS 规则组

来源：[Shield features](https://aws.amazon.com/shield/features/)、[AWS 安全博客：AMR 替代 Shield 自动缓解](https://aws.amazon.com/blogs/security/aws-shield-advanced-is-embracing-the-aws-waf-anti-ddos-managed-rule-group-what-changes-and-how-to-prepare/)

| 代际 | 机制 | 建基线速度 | 缓解速度 |
|------|------|-----------|---------|
| Shield Advanced L7 自动缓解（旧） | 流量基线（容量+构成），要求"双重统计显著偏离"才触发 | 数小时 | 事件级 |
| **WAF AMR（新，2027-01 全面替代）** | ML 模型检测基线偏离 + 自动应用规则 | **分钟级** | **秒级** |

**基线特征**：总流量容量 + 流量构成（请求属性组合），可选接入 Route 53 健康检查信号（更早发现攻击、更低误报）。

### 4.4 Azure DDoS Protection

来源：[Azure DDoS Protection 概览](https://learn.microsoft.com/en-us/azure/ddos-protection/ddos-protection-overview)

- "基于 ML 的网络流量画像"按公网 IP 自动配置三个缓解策略阈值（TCP SYN / TCP / UDP）
- 自适应实时调优：流量模式变化时自动更新最匹配的画像
- **约 24 小时学习期**后检测/缓解才生效（微软 deep-dive 演讲）
- 只管 L3/L4；L7 交给 Application Gateway WAF（与本文范式三衔接）

### 4.5 模式总结：基线模型服务的共性设计

```
┌────────────────────────────────────────────┐
│ 共性架构（Cloudflare/Google/AWS/Azure 一致）│
├────────────────────────────────────────────┤
│ 1. 分片键 = 客户（租户）× 属性维度          │
│ 2. 模型 = 轻量统计/浅层模型（非深度学习）    │
│    - 超球面距离 / 阈值画像 / 频次画像       │
│ 3. 离线批量重训（小时-天级周期）            │
│ 4. 在线只做打分（距离/偏离计算，O(1)）       │
│ 5. 冷启动保护（1h-24h 学习期内不告警）       │
│ 6. 输出可解释（哪个属性偏离、偏离多少）       │
└────────────────────────────────────────────┘
```

## 五、范式三：有监督载荷分类

> 已有文档的 Random Forest 章节讲了原理；这里补充**业界生产级规模**的做法和关键差异。

### 5.1 Cloudflare WAF Attack Score（零日检测）

来源：[Detecting zero-days before zero-day](https://blog.cloudflare.com/detecting-zero-days-before-zero-day)、[Making WAF AI models go brrr](https://blog.cloudflare.com/making-waf-ai-models-go-brr)、[Attack Score 文档](https://developers.cloudflare.com/waf/detections/attack-score/)

**训练数据从哪来（最值得借鉴）**：
- 用**现有 WAF 托管规则的判定结果做弱标注**（数亿请求）
- 加上**模糊变异（fuzzing）增强**：对已知攻击载荷做变换扩充样本
- 分 SQLi / XSS / RCE 三类独立模型

**推理**：
- ONNX 推理管线，实时处理数千万 req/s
- 输出 1-99 分：Attack ≤20 / Likely attack ≤50 / Likely clean ≤80 / Clean ≥99
- 实战战绩：在 Ivanti Connect Secure CVE 披露**之前**检出利用流量

**与规则引擎的关系**：ML 分数不替代规则，而是作为**独立信号**暴露给客户，让客户自定义组合（如 `wf.attack_score gt 50 and cf.threat_score gt 10`）。

### 5.2 Akamai Adaptive Security Engine

来源：[ASE 博客](https://www.akamai.com/blog/security/the-adaptive-security-engine-a-quantum-leap-forward-for-application)、[产品简介](https://www.akamai.com/site/en/documents/brief/akamai-app-and-api-protector-product-brief.pdf)

- ML + 统计 + 启发式混合，对每条策略的每个触发器**自调优**
- 新检测规则先在 Akamai 全部生产流量上**影子运行**，用 ML 验证后灰度上线
- 公开数据：检出提升 2x，误报降 5x；后续 ML 算法再降误报 4x

### 5.3 工程要点（生产级载荷分类器的共性）

1. **弱标注代替人工标注**：规则引擎判定 = 免费标签（有噪声但量大）
2. **数据增强**：fuzzing/编码变换/注释注入，覆盖绕过变体
3. **小模型 + 推理引擎**：梯度提升树或小型 NN，编译成 ONNX 原生推理（微秒级）
4. **分数化输出**：不输出二值，输出分数让用户自选阈值（不同客户误报容忍度不同）
5. **影子模式先行**：新模型先只记日志不拦截，验证精度后再切强制模式

## 六、范式四：行为序列自监督学习

> 已有文档的 LSTM/Transformer 章节是**有监督/重构**视角；Akamai 2025 年公开的 Masked Autoencoder 方法是**自监督**前沿，代表了一个明确的技术方向。

### 6.1 Akamai Masked Autoencoder Transformer

来源：[Identifying agentic automation](https://www.akamai.com/blog/security-research/identifying-agentic-automation-behavioral-telemetry)

**动机**：传统行为模型依赖**长序列**才能判断人机；AI Agent（自动化浏览）的行为序列很短，传统方法失效。

**方法**：
- 数据：**~350 万条无标注**鼠标事件序列（Bot Manager Premier 遥测），**35% 的事件被 mask**
- 架构：NLP 风格的 Masked Autoencoder Transformer，重建被遮盖的事件
- 学到的表示用于区分"人类交互"与"agentic 自动化"（短序列也有效）

**为什么自监督适合网关场景**：
1. 行为数据海量但**没有标签**（无法人工标"这是不是 bot"到序列级）
2. 自监督只需正常数据，天然匹配"异常检测只需正常样本"的范式
3. 预训练表示可微调到多个下游任务（bot 分类/账号接管/爬虫识别）

### 6.2 Cloudflare Bot Management 的实际技术栈（重要澄清）

来源：[Scalable machine learning at Cloudflare](https://blog.cloudflare.com/scalable-machine-learning-at-cloudflare)、[Residential proxy bot detection](https://blog.cloudflare.com/residential-proxy-bot-detection-using-machine-learning)、[Monitoring ML models for bot detection](https://blog.cloudflare.com/monitoring-machine-learning-models-for-bot-detection)、[Introducing Adaptive Intelligence](https://blog.cloudflare.com/introducing-adaptive-intelligence)

> ⚠️ **网上流传"Cloudflare 用 LSTM 检测 bot"——公开资料不支持**。实际公开文档：
- 主模型是 **CatBoost（梯度提升树）**，选择理由是"超低延迟推理"（博客系列标题就是 *Every request, every microsecond*）
- 为 **72%+ 的请求**产出最终 Bot Score；多个模型以**影子模式**在全部请求上运行
- 特征：请求指纹、行为信号、全网统计趋势
- GPU 训练（数万亿请求），生产环境有模型漂移告警
- **Adaptive Intelligence（2025）**：不再发布固定版本模型，持续重训

## 七、范式五：预测性自动扩缩容

> 这是"负载均衡"侧（而非安全侧）最重要的 ML 应用：**预测未来负载，提前扩容**。已有文档完全没有覆盖这一块。

### 7.1 Netflix Scryer（2013，生产系统鼻祖）

来源：[Scryer: Netflix's Predictive Auto Scaling Engine](http://techblog.netflix.com/2013/12/scryer-netflixs-predictive-auto-scaling.html)

```
历史需求数据（数周）
  │
  ▼
FFT 提取周级周期模式        ← 和 Microsoft SR 一样用 FFT！
  │
  ▼
Holt-Winters 三参数指数平滑预测
  │
  ▼
生成未来 N 分钟容量计划 → 提前扩容
```

- 动机：反应式扩容（CPU 超 60% 再扩）永远慢一拍，实例启动 10+ 分钟内服务已在降级
- 与反应式扩容**并存**：预测层处理可预期负载（早晚高峰），反应层兜底突发

### 7.2 AWS Predictive Scaling（现产品化）

来源：[New Predictive Scaling for EC2](https://aws.amazon.com/blogs/aws/new-predictive-scaling-for-ec2-powered-by-machine-learning/)、[评估博客](https://aws.amazon.com/blogs/compute/evaluating-predictive-scaling-for-amazon-ec2-capacity-optimization/)、[ECS 文档](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/predictive-auto-scaling.html)

- 官方描述："well-trained ML models" 预测流量（含日/周模式）；另一文档描述为**集成 ML**（ASG 自身模式 + AWS 数十亿数据点观测）
- 需要 **≥1 天**历史；预测**每 24 小时重新评估**
- 安全设计：**只根据预测扩容（scale-out），绝不根据预测缩容**——预测错了最多多花钱，不会服务中断

### 7.3 Azure VMSS Predictive Autoscale

来源：[Predictive Autoscale 文档](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-predictive)

- ML 预测 VM Scale Set 整体 CPU 百分比，提前扩容（lead time 可配，最长 60 分钟）
- **Forecast-Only 模式**：先只出预测不执行，人工验证预测质量后再启用执行
- 需约 7 天数据才开始预测

### 7.4 建模要点

1. **周期提取优先**：网关负载的日/周周期占方差大头，FFT/STL 提取周期后，剩余部分用简单平滑就够了（Scryer 证明于 2013 年）
2. **只扩不缩**：预测的单向使用是可靠性设计的关键（AWS/Azure 均如此）
3. **预测与反应分层**：预测层管可预期负载，反应层（HPA/阈值）管突发，两层叠加
4. **Forecast-Only 验证期**：任何预测系统上线前都应有一个"只预测不执行"的观察期

> ⚠️ 澄清：**没有主流云厂商文档化"用 LSTM/Prophet 做生产级预测扩容"**。LSTM/Prophet 扩容只出现在学术论文中。厂商文档只说"ML/集成预测"。立项材料如引用请以 Scryer（FFT+Holt-Winters）和 AWS/Azure 官方描述为准。

## 八、范式六：在线学习与概念漂移检测

> 已有文档讲了"滚动窗口重训"和"Welford 增量统计"，这里补充**正规的在线学习框架**和**统计上严格的漂移检测器**——两者是《轻量流式异常检测》的自然深化。

### 8.1 在线学习框架

| 库 | 特点 | 适用 |
|----|------|------|
| **River**（Python，creme + scikit-multiflow 合并） | 统一 API 的在线 ML：分类/回归/聚类/异常检测/漂移检测全都有 `learn_one`/`predict_one` 接口；内置 `ADWIN`、`DDM`、`PageHinkley` | 网关侧 Python 代理、快速原型 |
| **Vowpal Wabbit**（C++） | 极快在线线性模型（FTRL 等），常用于点击流/广告，单机每秒百万级更新 | 超高吞吐在线训练 |
| **Flink ML / Kafka Streams** | 流处理引擎内建状态算子，可用 KeyedProcessFunction 实现任意在线统计 | 与 Kafka 日志管道天然集成 |

```python
# River 示例：在线异常检测 + 自动漂移感知
from river import anomaly, drift, preprocessing

model = anomaly.HalfSpaceTrees(n_trees=10, depth=5)   # 在线孤立森林
drift_detector = drift.ADWIN(delta=0.002)             # 自适应窗口

for features in request_stream:
    score = model.score_one(features)
    model.learn_one(features)                          # 无标签也能学（HS-Trees 只建模正常）
    drift_detector.update(score)
    if drift_detector.drift_detected:
        reset_model_and_alert()   # 分布变了：重置模型 + 告警
```

### 8.2 漂移检测算法（比"定时重训"更精确）

| 算法 | 原理 | 特点 |
|------|------|------|
| **ADWIN**（Adaptive Window） | 维护变长窗口，检测到两子窗口均值统计显著不同则裁剪窗口 | 自适应窗口大小，误报率有理论界 |
| **DDM**（Drift Detection Method） | 监控分类错误率的二项分布，错误率超 2σ 预警、3σ 确认漂移 | 需要标签（错误信号） |
| **Page-Hinkley** | 累积和（CUSUM）变体检测均值漂移 | 简单快速，适合单指标 |
| **PSI**（Population Stability Index） | 分箱比较两个时期分布的 KL 散度类度量 | 金融风控标准做法，简单可解释 |

**与已有文档的关系**：《行为基线构建详细流程》7.5 节的漂移检测可以升级为 ADWIN/CUSUM 这类有统计保证的方法；《轻量流式异常检测》的"周期重训"可以升级为"漂移触发重训"（只在漂移时重训，而非固定周期）。

## 九、范式七：序列与图方法

### 9.1 请求序列建模（比 LSTM 便宜得多的选项）

已有文档的 LSTM/Transformer 章节假设用深度网络建模会话序列；但工业界在序列建模上有更轻的梯子：

| 方法 | 原理 | 成本 | 适用 |
|------|------|------|------|
| **n-gram 频次模型** | 统计正常会话中 URL/端点 n-gram 出现概率，低概率序列=异常 | Sketches 即可（CMS） | API 滥用/越权访问探测 |
| **马尔可夫链/HMM** | 状态转移概率矩阵，罕见转移=异常 | 状态数×状态数内存 | 会话劫持、业务逻辑攻击 |
| **URL Embedding（word2vec/FastText）** | 把 URL token 当"词"训练嵌入，异常=嵌入空间中的离群点 | 离线训练+在线查表 | 爬虫分类、路径遍历检测 |

这三个方法在"网关流量 ML"文献中长期存在，优势是**可解释、流式可增量更新、无 GPU**——与 stick tables/sketches 基础设施天然兼容。

### 9.2 图方法（GNN）

**生产级验证案例（支付网关）**：
- **Mastercard Decision Intelligence Pro**：在 Mastercard 网络图上为每笔交易生成路径（持卡人历史商户访问图），图技术 + RNN/Transformer 风格生成式模型，**~50ms** 出风险评分，年处理 1250 亿交易，官方报告欺诈检出提升平均 20%。来源：[CNBC 报道](https://www.cnbc.com/2024/02/01/mastercard-launches-gpt-like-ai-model-to-help-banks-detect-fraud.html)、[Mastercard 官方页](https://www.mastercard.com/global/en/business/cybersecurity-fraud-prevention/risk-decisioning/decision-intelligence.html)
- NVIDIA 也发布了 GNN+XGBoost 欺诈检测参考架构（带可解释性）——但这是参考实现，不是厂商生产声明

**网关安全场景（botnet/IP 关联图）**：⚠️ **无任何主要厂商公开文档化 GNN 用于 CDN/网关层的 botnet 检测**——目前只有学术论文。立项材料中应将其定位为"研究方向"而非"业界实践"。

## 十一、反例：不是所有网关都用 ML

### Fastly Next-Gen WAF（Signal Sciences）——信号驱动，决策层无黑盒 ML

### 11.1 出身背景：Etsy DevSecOps 文化的产物

Signal Sciences **2014 年由三位 Etsy 同事创立**：Andrew Peterson（CEO）、Nick Galbreath（CTO）、Zane Lackey（CSO）。Etsy 是 DevOps/DevSecOps 文化的发源地之一（持续部署、工程师自持安全、"往外讲安全"的社区传统），这个出身直接决定了产品哲学：

- **安全决策必须让工程师看得懂**：每个请求被标记为**人类可读的信号**（`SQLi`、`XSS`、`rate-anomaly` 等具名标签），阻断决策由"哪些信号 + 什么阈值"的**显式组合**构成，可以逐条回溯审计
- **反黑盒定位**：2010 年代传统 WAF（Imperva/F5/Barracuda）以黑盒规则库 + 营销话术中的 ML 著称，误报高、不可解释，工程团队普遍抵制。Fastly 2020 年收购新闻稿的原话就是把 Signal Sciences 定位为"**对现有不透明、割裂、僵化方案的替代**"（an alternative to the existing array of opaque, fragmented and inflexible solutions）

收购背景：2020 年 8 月 Fastly 以 **7.75 亿美元**（$2 亿现金 + 约 $5.75 亿 A 类普通股）收购 Signal Sciences，并入 NGWAF 产品线。来源：[Fastly 收购公告](https://www.fastly.com/press/press-releases/fastly-announces-agreement-acquire-signal-sciences)、[Software Stack Investing 分析](https://softwarestackinvesting.com/fastly-and-signal-sciences/)

### 11.2 架构与设计决策

来源：[Fastly NGWAF 产品文档](https://docs.fastly.com/products/fastly-next-gen-waf)、[One year later: Signal Sciences](https://www.fastly.com/blog/one-year-later-an-update-on-the-fastly-signal-sciences-story)

- 请求被标记为**信号**（攻击模式、异常、滥用），决策基于可配置**阈值**：标记、限速、阻断、放行或返回欺骗响应
- 架构强调**决策与执行解耦**：agent 在源站产生信号回传，边缘执行限速/阻断——判定发生在有业务上下文的地方
- **没有任何公开的评分式/生成式 ML 检测算法文档**

### 11.3 严谨修正："拒绝 ML"的说法不准确

信号集合里**包含统计类信号**（速率异常、时序基线偏离等）。准确的表述是：

| 层 | 有无 ML |
|----|--------|
| **检测层**（信号生产） | 有统计技术（速率/基线异常信号），无公开的深度学习模型 |
| **决策层**（阻断/放行） | **无黑盒 ML 评分**——全部是信号+阈值的显式组合，可审计 |

对比：Cloudflare Attack Score 也是"信号"，但它是**黑盒 ML 评分信号**（1-99 分，人类不知道为什么）；Fastly 的信号是**白盒规则信号**（命中了什么模式一目了然）。两者的差异在决策层，不在检测层。

### 11.4 为什么它可以不用 ML，而 Cloudflare/Akamai 必须用

| 因素 | Fastly/Signal Sciences 路线 | Cloudflare/Akamai 路线 |
|------|---------------------------|----------------------|
| **流量规模** | 客户级部署，单客户流量人工规则可覆盖 | 4600 万+ req/s 全网聚合，零日/Bot 演化速度超出人工策展能力，ML 是规模化的必须 |
| **市场细分** | 工程驱动型客户（API-first、DevOps 成熟），客户自己的团队有能力策展信号和阈值 | 广谱客户（大量无安全工程团队），需要模型自动适应 |
| **误报处理哲学** | 误报→客户工程师调阈值（分钟级，可解释） | 误报→模型重训/影子验证（小时-天级，自动但慢） |
| **判错代价** | WAF 决策可逆、可回滚，"慢一点但看得懂"是理性选择 | 大规模自动化下人工复核不可能，必须依赖模型+置信度 |

### 11.5 信号驱动的代价（诚实评估）

- **新攻击类型需要人工写信号**：零日爆发时响应速度慢于 ML 系统（ML 可从规则判定弱标注快速泛化，见本文范式三）
- **行为型攻击覆盖弱**：复杂 bot（模仿人类交互的自动化）的检测依赖行为序列模型（Akamai MAE 路线），纯信号体系覆盖不了
- 这解释了为什么 NGWAF 后来也强调把信号接入客户分析平台做二次分析——信号体系不排斥下游分析，只是拒绝把黑盒模型放进阻断路径

**启示**：ML 不是网关安全的必要条件。信号+阈值架构的优势是**可解释、可审计、误报可控**——这正是《轻量流式异常检测》快路径的设计哲学。ML 应该作为信号的**补充生产者**（如 Cloudflare Attack Score 也是一个"信号"），而不是替代信号体系。**选信号驱动还是 ML 驱动，取决于流量规模、团队构成、客户细分——不是技术优劣，是场景匹配。**

### 11.6 检测信号全景与统计机制

来源：[Using system signals](https://www.fastly.com/documentation/guides/next-gen-waf/signals/using-system-signals)、[About threshold configurations](https://www.fastly.com/documentation/guides/next-gen-waf/thresholds/about-threshold-configurations)

**信号四大类**（系统信号，另有用户自定义信号）：

| 类别 | 代表信号（短名） | 说明 |
|------|----------------|------|
| **攻击 Attack** | `SQLI`、`XSS`、`CMDEXE`、`TRAVERSAL`、`BACKDOOR`、`LOG4J-JNDI`、`AWS-SSRF`、`USERAGENT` | 含攻击载荷的恶意请求 |
| **异常 Anomaly** | `ABNORMALPATH`、`BHH`（HTTP 走私）、`SCANNER`、`NULLBYTE`、`MALFORMED-DATA`、`SIGSCI-IP`（全网恶意 IP）、`SANS`（SANS ISC 情报源） | 不必然恶意但异常 |
| **Bot** | `SUSPECTED-BOT(.HEADLESS/.AI-CRAWLER/.AI-FETCHER)`、`VERIFIED-BOT.*`（8 类验证 bot）、`COMPROMISED-PASSWORD` | 多数仅 Edge 部署可用 |
| **信息性 Informational** | `HTTP403/404/429/4XX/500/503/5XX`、`TORNODE`、`DATACENTER`、`DOUBLEENCODING`、`FAIL-OPEN`、`ALLOWED` | 正常请求属性 |

**统计机制**：
- 每个信号在 **1 分钟周期**内被标记的请求数，聚合成时序图（官方原文："counts the number of requests tagged with a particular signal during one minute periods"）
- 限流场景：按**客户端标识**（IP 或自定义 client key）统计 threshold signal 数量

**窗口语义——不是严格滑动窗口**：

官方描述的是 **threshold + interval + duration** 三元组（例：1 分钟内 10 次 → 封禁 5 分钟），计数为分钟桶粒度。文档没有 "sliding window" 表述，语义上更接近"**固定分钟桶计数 + flag 后持续封禁**"，与 HAProxy stick-table `http_req_rate(10s)` 那种真滑动窗口**不同**。两个工程细节：

- **多 agent 部署**：本地计数器独立判定（不等云端），跨 agent 全局计数由云端聚合；断链时聚合暂停
- **Edge 部署**：分布式计数有误差——官方承认"可能需要最多 2 倍请求数才能触发匹配"，建议 100 RPS 以上测试

阈值配置分三类：**高级限流规则**（用户定义，Premier 平台，每 workspace 最多 15 条）、**攻击阈值**（Fastly 预定义，按 workspace 对全部攻击信号生效）、**信号阈值/站点告警**（用户按特定信号定义）。flag 后阻断/记录持续 duration，block 与 log 动作的 flag 互不竞争。

### 11.7 Agent 与云端的分工：本地决策平面 + 云端控制平面

来源：[About the architecture](https://www.fastly.com/documentation/guides/next-gen-waf/concepts/about-the-architecture)、[Getting started with the agent](https://www.fastly.com/documentation/guides/next-gen-waf/agent-management/getting-started-with-the-agent)

```
┌─ 本地（数据平面 + 本地决策平面）──────────────┐
│ module ──RPC(UDS/TCP)──▶ agent（Go 编写）      │
│   传请求              │ ① 实时信号标记/规则判定 │
│   ◀───────────────────┘ ② 本地计数器（阈值/限流）│
│                          ③ 脱敏                │
└──────────────┬───────────────────────────────┘
               │ 每 30 秒异步双向
               ▼
┌─ 云端（控制平面 + 全局聚合）─────────────────┐
│ ④ 下发：规则/列表/配置更新                      │
│ ⑤ 上收：脱敏后的可疑请求数据 → dashboard/集成   │
│ ⑥ 多 agent 全局计数聚合（限流的全局视图）        │
│ ⑦ NLX 威胁情报：全网客户攻击数据 → IP 信誉 →     │
│    下发 agent（命中即打 SIGSCI-IP 信号）        │
└──────────────────────────────────────────────┘
```

**职责边界**：
- **agent（本地）**：实时信号标记、规则/阈值判定、本地计数、脱敏、把决策回给 module 执行
- **云端引擎（AWS 西部多可用区）**：配置下发、数据上收与可视化、**多 agent 计数聚合**、NLX IP 信誉（订阅网络共享威胁情报）
- 关键设计：**判定不依赖云端**——云端只做控制平面和全局聚合，本地计数器独立生效

**断云降级（官方明确文档化）**：
- agent 继续用最后配置检测攻击/异常、继续执行阻断、本地计数器继续累计
- 跨 agent 聚合暂停；**请求日志不排队**（dashboard 数据出现空窗，恢复后从当前时刻继续）
- 收不到新配置、新检测更新、地理库更新

**模块超时与 fail-open**：module 等待 agent 响应仅 **100ms**（IIS/.NET 200ms），超时 fail-open 放行——这个超时量级印证了"module 与 agent 本地 RPC"的假设。被放行的请求会打上 `FAIL-OPEN` 信号。

### 11.8 部署拓扑与日志同步

**agent 部署位置**：默认同机，但不是必须：

| 拓扑 | module 位置 | agent 位置 | 通信 |
|------|------------|-----------|------|
| **Module-agent（默认）** | Web 服务器内（NGINX/Apache/IIS/HAProxy/Kong 插件）或应用层（.NET/Java/Node.js RASP） | **同机** | UDS（Unix domain socket） |
| 分离部署 | Web 服务器内 | **独立机器**（一台 agent 服务多台 Web 服务器） | TCP |
| 反向代理 | 无（agent 兼任代理） | 流量路径中 | — |
| Edge / Cloud WAF | Fastly CDN/Compute 即 module | **无本地 agent**（Fastly 托管） | — |

**日志同步——不需要 Fluentd/Filebeat 等外置搜集器**：
- **agent → 云端**：每 30 秒异步上传**脱敏后**的请求/响应数据（自研通道），是唯一上云路径；断云不排队不补传
- **云端 → 下游**三种消费方式：① dashboard/搜索；② **REST API request feed**（游标分页，Google SecOps 官方采集器即拉此 API 写入 GCS）；③ 集成/告警（Splunk、Datadog、Slack、webhook 等）

对自研网关的启示：**检测数据面和控制面分离后，日志上传可以内嵌在检测 agent 里**（自带缓冲+脱敏+批量上传），不必强依赖外部日志栈——但代价是断链时的数据空窗，需要在"简单"与"可靠性"之间做取舍（外置 Kafka 管道可解决，参考《waf-log-storage-practices》）。

### 11.9 与 DataDome 的对比：本地 PDP vs 云端 PDP

DataDome 是另一个常被一起讨论的 bot 防护厂商，但**决策平面位置正好相反**：

| 维度 | Signal Sciences / Fastly NGWAF | DataDome |
|------|-------------------------------|----------|
| **判定位置** | **本地 agent 判定**（规则全量下发，断云仍可检测+阻断） | **云端判定**（module 采集指纹，同步调用 DataDome API 等待 ML 裁决） |
| module 角色 | 传递请求 + 执行 agent 决定 | 采集指纹 + 同步调用 API（官方称 ~2ms，35+ PoP/区域边缘缓存，如 CloudFront Regional Edge Cache） |
| 检测技术 | 白盒信号+阈值，决策层无黑盒 ML | ML 中心化（官方称日处理 5 万亿+ 信号），裁决 = allow / challenge / block |
| 失联行为 | module 100/200ms 超时 fail-open；agent 离云继续工作 | module 超时按配置决定放行/拦截 |
| 哲学 | 可用性与可解释性优先（Etsy 工程文化） | 检测精度优先（ML 集中云端，全球视图） |

用 PDP/PEP 术语：Signal Sciences = **本地 PDP**（策略决策点在客户机器上），DataDome = **云端 PDP + 本地 PEP**。来源：[AWS 博客](https://aws.amazon.com/blogs/apn/preventing-online-fraud-and-attacks-with-aws-and-datadome-real-time-bot-protection/)、[DataDome 产品页](https://datadome.co/products/bot-protection/)

#### 11.9.1 澄清："ML 中心化"的准确含义——中心化的是智能，不是推理

DataDome 并非"所有流量回到一个中心大脑"。真实架构是 **全球训练 + 区域服务**：

```
训练/模型管理/威胁情报（中心）          ← 真正"中心化"的部分
        │ 模型分发
        ▼
26 个部署点（20+ AWS 区域，35+ PoP）     ← 推理在这里
  每个区域一套 DataDome API + Route 53 按区域解析
        ▲
        │ 同步调用（~2ms，最近的区域）
  客户 module/Lambda@Edge（采集指纹 → 等裁决）
```

- CloudFront 集成时，DataDome API 部署在**每一个 CloudFront Regional Edge Cache**，Lambda 就近查询（450+ CloudFront PoP 路由到区域边缘缓存）
- 每个请求的同步调用半径是"到最近区域"，不是跨洋回源——2ms 是这么来的

#### 11.9.2 吞吐账：扛得住的量化依据

官方称日处理 **5 万亿+ 信号**：

```
5×10¹² / 86400 秒 ≈ 5,800 万次判定/秒（全球均值）
÷ 26 个部署点 ≈ 220 万次判定/秒/区域
```

按单次推理 0.5ms CPU、单机 3-6 万 RPS 估算，每区域平均 **40-70 台推理服务器**即可承接均值——对融资充足的厂商完全可行，DDoS 峰值靠 AWS 弹性扩容（官方明说"与 AWS 合作实现了最快的扩容"）。

#### 11.9.3 真正的风险点

| 风险 | 实际情况 | 缓解手段 |
|------|---------|---------|
| **请求路径网络依赖** | 每个请求都要等云端裁决——与 Signal Sciences 的本质差异 | module 超时（CloudFront 配置默认 **300ms**）+ fail-open/fail-closed 可配；fail-open = 故障期裸奔 |
| **区域级故障** | 单区域 API 挂了影响该区域流量 | Route 53 DNS 切换到其他区域，但跨区 RTT 飙升（2ms → 几十至上百 ms） |
| **延迟方差** | 2ms 是 vendor 自报的最优情形（就近 PoP）；无 PoP 区域、DNS 故障转移时大幅恶化 | module 端超时封顶单请求最坏等待 |
| **成本线性增长** | 每个请求一次同步调用 = 推理成本随客户流量线性涨，是厂商核心 COGS | 这是 DataDome 按请求计费贵的根本原因 |
| **全球模型一致性** | 新模型/新情报推送到 26 个区域有传播延迟 | 安全场景下秒级延迟可接受（Signal Sciences 配置下发也是 30s） |

**结论**：DataDome 的架构对"安全 SaaS 厂商"是成立的——它把规模问题转化为"多云区域部署 + 弹性扩容"的经典云问题，而不是单点中心化的死结。但代价是每个客户请求都多了一个网络依赖。

#### 11.9.4 决策平面位置的三种模式（频谱）

| 方案 | 判定位置 | 请求路径依赖 | 智能新鲜度 | 适用者 |
|------|---------|-------------|-----------|--------|
| **Cloudflare 模式** | 边缘节点内联推理（模型复制到每个节点） | **零**（WAF 就是边缘本身） | 高（持续重训，Adaptive Intelligence） | 自己拥有边缘网络的 CDN |
| **DataDome 模式** | 最近区域 API（同步调用，2-300ms hop） | 一个网络依赖 | 最高（中心训练全球视图） | 有 PoP 网络的安全 SaaS |
| **Signal Sciences 模式** | 客户本地 agent | **零**（断云可用） | 配置下发延迟 30s | 自建网关/本地部署产品 |

**对自研网关（haproxy-ui）的选型结论**：DataDome 模式不成立——不可能要求客户的每个请求同步等待自家云端 API。可选项是后两种：① HAProxy 内联轻量判定（stick tables + 规则 + 本地小模型，Cloudflare 模式的本地版）；② 本地 agent 外接判定（Lua/SPOE，Signal Sciences 模式），云端只做训练和配置下发。

### 11.10 与 HAProxy 的关系（澄清）

**HAProxy 不是 Signal Sciences 的核心技术栈，反而是竞品**：

- HAProxy 只是 NGWAF 众多**接入模块**之一（与 NGINX、Apache、IIS、Kong、Traefik 平级）
- 且 HAProxy 有**两种官方模块**：[原生 Lua 模块](https://www.fastly.com/documentation/guides/next-gen-waf/setup-and-configuration/module-agent-deployment/haproxy-module/)（`lua-load .../sigsci/SignalSciences.lua`）和 [HAProxy SPOE 模块](https://www.fastly.com/documentation/guides/next-gen-waf/setup-and-configuration/module-agent-deployment/haproxy-spoe-module/)（Stream Processing Offload Engine）
- HAProxy Enterprise WAF 与 Fastly NGWAF 是同类竞品（wafplanet 等评测站直接对比）
- Fastly 自家 CDN 边缘核心是 **Varnish**（VCL），也不是 HAProxy

**对 haproxy-ui 的启示**：Signal Sciences 的价值不在代理层（不自建代理，寄生在客户已有的 NGINX/HAProxy 上），而在**检测决策层与数据平面的解耦**——module 只做"拦截 + RPC 转发 + 执行决定"，agent 做检测，云端做控制。haproxy-ui 可复用的正是这个模式：HAProxy 做数据平面，通过 **Lua 或 SPOE 外接检测 agent**（SPOE 原生就是为这种外挂分析设计的），agent 本地判定 + 本地 stick-table 计数，配置由管理面下发。

## 十三、建模方法选择决策树

```
你的场景是什么？
│
├─ 监控网关指标（RPS/错误率/延迟）？
│    ├─ 有明显日/周周期 → STL 分解 / Robust（Datadog）/ S-H-ESD
│    ├─ 无周期、短窗口 → 移动平均+sigma（Basic）/ CUSUM
│    └─ 海量序列、无精力调参 → 谱残差 SR（免训练、O(n log n)）
│
├─ 多租户 L7 攻击检测（CDN/网关 SaaS）？
│    ├─ 每客户每属性独立轻量模型（超球面距离/阈值画像）
│    ├─ 离线批量重训 + 在线 O(1) 打分
│    └─ 冷启动学习期（1h-24h）不告警
│
├─ 载荷攻击分类（WAF 零日）？
│    ├─ 规则引擎判定做弱标注 + fuzzing 增强
│    ├─ 梯度提升树/小 NN → ONNX 微秒级推理
│    └─ 输出分数（1-99）+ 影子模式先行
│
├─ Bot/人机区分？
│    ├─ 梯度提升树 + 指纹/行为特征（CatBoost 路线）
│    ├─ 短序列挑战 → 自监督 Masked Autoencoder（Akamai 路线）
│    └─ 轻量替代 → n-gram/马尔可夫链（可解释）
│
├─ 负载均衡容量预测？
│    ├─ FFT/STL 提周期 + Holt-Winters 预测（Scryer 模式）
│    ├─ 只扩不缩 + Forecast-Only 验证期
│    └─ 与反应式扩容分层并存
│
└─ 流量工程/调度优化？
     ├─ 现实：LP 优化 + ML 加速求解（TEAL）
     └─ RL：预研/仿真定位，勿写生产架构
```
