# i18n evaluation (zh-CN) — 2026-09-09

结论先行：**建议做，但放到独立迭代**。工作量主要不在接入库，而在文案
抽取与审校；混在功能迭代里会拖慢两边。

## 现状

- UI 文案全部为英文字面量，硬编码在 `src/routes/**` 与
  `src/components/**` 中。
- 粗略统计（grep 字符串字面量 + JSX 文本）：约 **900–1100 条**用户可见
  文案，其中约 60% 在 15 个节点详情 tab 组件里。
- 错误消息（toast、API `error` 字段）多数为英文短句，服务端返回的
  error 文案也需一并处理才完整。

## 方案对比

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| react-i18next | 生态成熟、命名空间/懒加载/复数支持全 | 引入运行时与 provider；key 管理有约定成本 |
| 轻量字典模块（自研 `t(key)`） | 零依赖、SSR 简单、tree-shake | 复数/插值/上下文需自己实现 |

建议：**自研轻量字典**。本项目文案以短句为主、无复杂复数，SSR 场景下
避免再引入一层 provider；字典文件按领域拆分（`src/i18n/zh-CN/*.ts`），
缺失 key 回退英文并可在 lint 中报警。

## 实施拆分（若立项）

1. 抽取骨架 + `t()` 实现 + 语言切换（0.5 天）
2. 核心页面（登录/概览/节点列表/节点详情框架）约 300 条（1–2 天）
3. 其余 tab 与 toast 文案（2–3 天）
4. 服务端 error 文案 + 测试断言适配（1 天）

总计约 1 周。风险：E2E 断言大量依赖英文文案（20 个场景），
需要在实现时让断言走 `data-testid` 或保留英文 key 作断言锚点。
